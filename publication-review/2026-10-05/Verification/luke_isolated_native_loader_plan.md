## Why direct-generated .oleans can use native definitions

The author-authored Lake `precompileModules` policy has not been run. The existing frozen custom `.oleans` were independently produced through direct Lean CLI without a new package setup. The native retry must match that metadata rather than manufacture a different package identity.

The pinned [module package extension](https://github.com/leanprover/lean4/blob/5045d0056413266e57c625dcd7c365b10e377c52/src/Lean/Compiler/ModPkgExt.lean#L46) stores the package identifier as an environment extension. `getSymbolStem` reads that identifier from an imported module and applies package-aware mangling. With package `none`, the custom definitions use the `l_` prefix. Official dependency modules retain their own imported package identifiers, such as `mathlib`, and use the corresponding `lp_mathlib_` prefix. The [frontend import path](https://github.com/leanprover/lean4/blob/5045d0056413266e57c625dcd7c365b10e377c52/src/Lean/Elab/Import.lean#L140) sets the current module's package from `package?`, whose default is `none`. Generating custom C with the same direct command policy and no new `--setup` therefore preserves the direct `.olean` identity. The custom C's actual symbol and initializer names must still be inspected after generation.

Native availability is resolved by the interpreter from the environment's ordinary IR declarations, their package-aware names, and the loaded process symbols. No `precompileModules` boolean is consulted in that lookup path. In the pinned [IR interpreter](https://github.com/leanprover/lean4/blob/5045d0056413266e57c625dcd7c365b10e377c52/src/library/ir_interpreter.cpp#L827), native symbol lookup first tries the boxed symbol, then the unboxed or explicitly exported symbol. The default `interpreter.prefer_native` value is true. Windows lookup enumerates all loaded process modules and uses `GetProcAddress`, so a correctly loaded and exported dependency DLL participates in the same lookup. The existing direct replay is already evaluating the relevant Count IR, which confirms that the declaration metadata is available; this does not by itself confirm the future native symbol matches.

The interpreter caches failed native lookups as well as successful ones. The native libraries must consequently be loaded in a fresh process **before** importing or evaluating any custom Count definitions. A late library load into the current long-running certificate process is disallowed by the pinned initializer contract and is not proposed.

## Loader and initializer procedure

The pinned [C shell startup](https://github.com/leanprover/lean4/blob/5045d0056413266e57c625dcd7c365b10e377c52/src/util/shell.cpp#L312) calls `lean_enable_initializer_execution` before processing command-line options. Option processing runs while `IO.initializing` is true. In [ImportingFlag](https://github.com/leanprover/lean4/blob/5045d0056413266e57c625dcd7c365b10e377c52/src/Lean/ImportingFlag.lean#L41), `Lean.initializing` is `IO.initializing || importingRef`, so environment-extension registration is permitted in this phase. After option processing, the shell ends IO initialization and imports the source normally.

The exact command-line spelling is `--plugin=file=initializer`, with an equals sign before the explicit initializer name. The pinned [Shell option branch](https://github.com/leanprover/lean4/blob/5045d0056413266e57c625dcd7c365b10e377c52/src/Lean/Shell.lean#L412) splits at that equals sign and calls `Lean.loadPlugin`. The older docstring's colon spelling is not the implementation to follow.

The first DLL should be loaded by `--load-dynlib=ABSOLUTE_NONMATHLIB_DLL`. Its symbols become available, but this command deliberately does not pretend to initialize them. The second should be loaded by `--plugin=ABSOLUTE_MATHLIB_CUSTOM_DLL=ACTUAL_COUNT_INITIALIZER`. The anticipated root initializer, if C emission confirms the current package and non-module policy, is `initialize_K4Ramsey_Constructions_Final3840_Count`. The anticipated name is not a fabricated wrapper. It must be an actual function emitted by the pinned C generator from the frozen Count module. `loadPlugin` resolves that exported function and runs it with `builtin=1`. Its emitted recursive calls initialize every relevant imported module, including the first DLL's dependency modules. The pinned emitter's idempotent guards preserve once-only initialization.

This initializer chain is essential: `bCache`, `dCache`, and `pathsCache` are computed global arrays, not link-time substitutes. The [C emitter](https://github.com/leanprover/lean4/blob/5045d0056413266e57c625dcd7c365b10e377c52/src/Lean/Compiler/LCNF/EmitC.lean#L1006) emits the runtime/meta or legacy initializer calls according to the actual imported modules and package identifiers. No initializer may be omitted, stubbed, or replaced by a guessed return value.

The later `.olean` import runs `runInitAttrs`. The pinned [InitAttr import code](https://github.com/leanprover/lean4/blob/5045d0056413266e57c625dcd7c365b10e377c52/src/Lean/Compiler/InitAttr.lean#L158) obtains each imported module's package, computes its initializer name, and resolves it in the loaded process. Already run C initializer guards make this harmless. If there is no native module initializer it falls back to interpreted initializers, but a native pilot must record whether that fallback occurred rather than treating it as evidence of accelerated Count execution.

For the future actual certificate retry, the original theorem file and statement stay unchanged. `native_decide` constructs its own fresh auxiliary Bool declaration, compiles it to ordinary Lean IR, and calls `evalConst`. Calls into the previously loaded source-identical Count definitions can then use their native implementations. The exact [native tactic source](https://github.com/leanprover/lean4/blob/5045d0056413266e57c625dcd7c365b10e377c52/src/Lean/Meta/Native.lean#L39) still executes the Bool and creates the explicitly named native-evaluation axiom only after a true result. Merely loading the DLL does not pass the theorem. The ordinary rational-normalization theorem remains kernel checked, and the arithmetic endpoint's compiler/runtime trust remains explicit.
